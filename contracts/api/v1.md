# API, v1

- **Status:** proposed
- **Producer:** backend (Supabase: PostgREST over `public`, one edge function)
- **Consumer:** frontend (`frontend/src/lib/api.ts`)

Money is always an integer `*_minor` beside a `currency` (AGENTS.md item 4).
Timestamps are ms since the epoch, UTC. Business dates are `YYYY-MM-DD`.
`bytea` columns arrive as `\x`-prefixed hex; the client strips the prefix.

**Errors.** A rule the server refuses comes back as Postgres SQLSTATE
`P0001` (from PostgREST) or HTTP 400 `{ "error": "…" }` (from the edge
function), with a sentence written for the person reading it. Anything else
is a fault, not a refusal.

## Reads (PostgREST, any member)

Membership is an open tenure, a committee seat, or an auditor appointment.
Every read is filtered to the caller's societies; a stranger reads nothing.

| Path | Returns |
|---|---|
| `GET /rest/v1/ledger?society_id=eq.X&order=seq` | One row per money posting with `balance_minor` (running cash), reversal links both ways, `tier`, `fingerprint`. `amount_minor`, `balance_minor` and `limit_minor` are **never null**: only postings that move money appear, and every proposal carries its limit |
| `GET /rest/v1/proposals?society_id=eq.X` | Proposals with `state`, `approvals[]`, counts, the snapshotted `tier`/`required`/`seated`/`limit_minor` |
| `GET /rest/v1/disputes?society_id=eq.X` | Flags with `is_open`, `notes[]`, `handle` (a pseudonym) |
| `GET /rest/v1/flat_dues?society_id=eq.X` | Per flat: `charged_minor`, `paid_minor`, `outstanding_minor`, **never null** (0 when nothing applies). Generated types say nullable only because every view column is typed so |
| `GET /rest/v1/chain_entries?society_id=eq.X&order=sequence` | The raw chain, for client-side verification |
| `GET /rest/v1/committee_seats`, `people`, `flats`, `auditor_appointments` | Registry. `people`: a resident sees committee, auditors and themselves only |

| RPC (`POST /rest/v1/rpc/…`) | Returns |
|---|---|
| `api_me(p_society?)` | The caller: seat, tenure (with handle), auditor years, society |
| `api_summary(p_society)` | Balance, per-month in/out, FY spend by category, dues totals. Every total the dashboard shows |
| `api_report(p_society, p_fy)` | The annual report: income and expenditure, balance sheet, reversals, **adjusting entries against closed years**, structuring aggregates, opinions, sign-offs |
| `api_years(p_society)` | Each FY with its headline opinion and history |
| `api_structuring(p_society)` | Below-limit payments to one payee that cross the limit within the window |
| `api_head(p_society)` | `{ hash, highest_sequence, entry_count, as_of, format_version }` |
| `api_preview_charge(p_society, p_flat_set, p_total)` | Committee: what a charge would allocate |

## Signed writes (edge function `api`)

`POST /functions/v1/api/<route>` with the user's bearer token. The function
authenticates the caller, signs with their server-held key, and calls the
service-only RPC. Clients cannot call those RPCs themselves.

| Route | Body | Result |
|---|---|---|
| `/propose` | `{ society, proposal }` | `{ seq, status }`. The proposer's own approval is cast when their seat lets it count |
| `/cast` | `{ society, seq, decision }` | `{ status }`: `open`, `posted` or `declined` |
| `/signoff` | `{ society, month, note? }` | `{ seq }`. President only |
| `/close-year` | `{ society, fy, opinion, statement }` | `{ seq }`. The appointed auditor only, after the year ends |
| `GET /head?society=` | | `{ head, signature, public_key }`: the head tuple signed with the society's head key |

`proposal` fields by action are those of the `proposal` kind
([`../chain/kinds/ledger.v1.md`](../chain/kinds/ledger.v1.md)); the server
computes tier, count, allocation and dates itself and ignores any client
value for them.

## Society lifecycle and setup (#10)

A society is `draft` when the platform creates it, `setup` once its president
first saves, and `open` after "Open the ledger". Nothing is chained before
`open`. **Every write in the sections above refuses unless the society is
`open`**, with `This society is not open yet.`

`api_me(p_society?)` gains `society.status`, `posts: [{ post_id, post_title,
seat_role, tasks[] }]` (the caller's posts, from the latest `tasks_set`) and
`tour_done_at` (ms or null).

### Platform admin (edge function `api`)

The caller's auth user must be in `platform_admins`; anyone else gets HTTP 403
`{ "error": "…" }`. The platform admin holds no seat, tenure or key, and no
route here writes into an `open` society.

| Route | Body | Result |
|---|---|---|
| `POST /platform/societies` | `{ name, city, address, registration_no?, flat_count, fy_start_month, president: { full_name, personal_email, phone } }` | `{ society }`. Status `draft`; currency is `INR` |
| `GET /platform/societies` | | `[{ society, name, status, president_name, president_email_masked, created_at }]` |
| `POST /platform/societies/:society/president` | `{ full_name, personal_email, phone }` | `{ ok }`. Replaces the president. Refused once `open` |

Refusals (400): name missing or over 120 characters; `flat_count` not 1–500;
`fy_start_month` not 1–12; email not valid.

### Setup (the president of a `draft` or `setup` society)

The draft is one JSON object saved step by step. A save replaces that step's
key only and returns every problem in the whole draft, so the review screen can
list them.

| RPC | Returns |
|---|---|
| `api_setup_get(p_society)` | `{ status, draft, problems[] }` |
| `api_setup_save(p_society, p_step, p_value)` | `{ draft, problems: [{ step, path, message }] }`. `p_step` is one of the keys below. `draft` carries the `post_id`s minted for new posts |

```jsonc
{
  "details":   { "name": "", "city": "", "address": "", "registration_no": null, "fy_start_month": 4 },
  "posts":     [{ "post_id": "pst_a1b2c3d4", "post_title": "Treasurer", "seat_role": "treasurer" }],
  "committee": [{ "post_id": "pst_a1b2c3d4", "full_name": "", "personal_email": "", "phone": "" }],
  "flats":     [{ "flat_key": "f1", "label": "A-101", "has_parking": false }],
  "residents": [{ "person_key": "r1", "flat_key": "f1", "kind": "owner", "owner_key": null,
                  "resides": true, "full_name": "", "personal_email": "", "phone": "" }],
  "money":     { "approval_limit_minor": 500000, "monthly_charge_minor": 250000, "currency": "INR" },
  "tasks":     [{ "post_id": "pst_a1b2c3d4", "tasks": ["propose_expenses"] }]
}
```

- `posts`: the three fixed posts come pre-filled and cannot be removed;
  further posts have `seat_role` `member`. `post_id` is minted by the server on
  first save of a new post (send `null`).
- `flats`: registry ordinals follow array order and become permanent at open.
- `residents`: `kind` `owner` or `tenant`; a tenant names its owner's
  `person_key`. Joint owners are two `owner` rows on one flat. `resides` is
  display only; access comes from the tenure.
- A committee member who also lives in the society appears in both lists with
  the same `personal_email`, and becomes one person.
- `money.monthly_charge_minor` is a setting, not an entry: charges are still
  proposed and approved after open.

Problems the review screen must show, and that block opening: fewer than 3
committee members; treasurer or secretary missing; one person in two fixed
posts; a flat with no owner; a tenant whose owner is not on the same flat; a
duplicate `personal_email` across different names; a task not in the
catalogue; no minutes uploaded. `approval_limit_minor` of `0` is a **warning**,
not a block: it sends every entry to the committee.

### Election minutes (edge function `api`)

| Route | Body | Result |
|---|---|---|
| `PUT /setup/minutes?society=` | Raw bytes, `Content-Type: application/pdf`, at most 10 MiB, header `X-File-Name` | `{ sha256, size_bytes, file_name }` |

Re-uploading replaces the file until open. The SHA-256 shown is the server's
own computation; at open the server reads the stored object again and chains
that hash, never a client value. Refusals: not a PDF, over 10 MiB, society
already open.

### Open the ledger (edge function `api`)

| Route | Body | Result |
|---|---|---|
| `POST /open-society` | `{ society, confirm }` | `{ head }`, the head tuple after opening |

`confirm` must equal the society's name exactly. In one transaction the server
appends `society_opened`, `document_attached` and one `tasks_set` per post
([`../chain/kinds/society.v1.md`](../chain/kinds/society.v1.md) *Order at
open*), creates people, flats and tenures with their handles, records the
seats, and sets the society `open`. If any step fails, nothing is kept. Keys
are registered on each admin's first signature, as today. Refusals: any
blocking problem above (the first one is returned), `confirm` mismatch, caller
not the president, society already open.

Sign-in IDs and enrolment mail are the sign-in contract's (#11), not this one.
Who vouches for an officer's personal email is still open (`docs/GOALS.md`);
when it is settled, this route gains a refusal or a step, additively.

### After open

| RPC | Who | Returns |
|---|---|---|
| `api_set_post(p_society, p_post_id, p_title, p_holder, p_tasks)` | President | `{ seq }`. Appends a `tasks_set` with the full new state. `p_post_id` null creates a `member` post. Refusals: a fixed post's title change that leaves it empty, a holder without the post's seat, an unknown task |
| `api_tour_done(p_society)` | Anyone | `{ ok }`. Sets `tour_done_at` |

`api_add_person`, `api_add_tenure`, `api_close_tenure` and a `response` flag
note now require the matching task (`manage_residents`, `respond_to_flags`)
instead of any committee seat. `expense` and `charge` proposals require
`propose_expenses` and `raise_monthly_charges`. Approving is unchanged: any
admin whose seat counts may approve, task or not.

## Sign-in (#11)

Everyone, officers and residents alike, signs in with a **ClearFunds ID** and
a 6-digit code emailed to their **personal** address. No passwords.

### IDs

| Holder | Format | Lifecycle |
|---|---|---|
| A post | `<post-slug>@<society-slug>.com`, e.g. `treasurer@gulmohar.com`, `joint-secretary@gulmohar.com` | Created with the post. Follows the post: when its holder changes, the ID points at the new holder and the old holder's sessions end. A vacant post's ID cannot sign in |
| A resident's tenure | `<first-name>.<flat-slug>@<society-slug>.com`, e.g. `riya.a101@gulmohar.com` | Created with the tenure, closed with it, **never reissued**. A collision gets a numeric suffix: `riya2.a101@…` |

Slugs are lowercase ASCII: letters and digits only for the society (at most 20,
from the society's name with `chs`, `society`, `co-op` and `housing` dropped),
letters, digits and hyphens for a post title, letters and digits for a first
name and a flat label. The ID is a reference: **no mail is ever sent to it**,
and the domain need not exist.

### Routes (edge function `api`, no bearer token needed)

| Route | Body | Result |
|---|---|---|
| `POST /auth/request-code` | `{ clearfunds_id }` | `{ sent: true }`, always the same for a known, unknown or closed ID, so IDs cannot be probed. A code goes to the personal email only for an active ID |
| `POST /auth/verify-code` | `{ clearfunds_id, code }` | `{ access_token, refresh_token, expires_at }`, a Supabase session the client installs with `setSession` |

Errors (HTTP 400, `{ error }`): `That code is wrong or has expired.` (also
for an unknown or closed ID); `Too many attempts. Try again in N minutes.`
after 5 wrong codes for one ID within 15 minutes; `Wait a minute before
asking for another code.` within 60 seconds of the last request for that ID.
Codes expire after 10 minutes.

### Reads

- `api_my_ids(p_society)` -> `[{ clearfunds_id, kind: post | resident, post_title?, flat? }]`,
  the caller's IDs that can sign in now.
- A committee member reads `logins` for their society: `clearfunds_id`,
  `kind`, `post_id?`, `tenure_id?`, `active`, holder name. Never the personal
  email.

### Enrolment

When an ID becomes active for a person — at open, when a post's holder
changes, when a tenure is added — that person is mailed at their personal
address: their ClearFunds ID, the society, and what the ID lets them do. An
officer's mail names their post, the approvals it takes part in and their
assigned tasks. A tenant's mail says that **the owner of their flat can see
the disputes they raise** (AGENTS.md item 11). The mail never says the
address was verified (item 13).

### What the ID is not

Access comes from an open tenure, a committee seat or an auditor appointment,
never from the ID. Someone who obtains a session by other means — Supabase's
own email OTP for their personal address — gets exactly the access their
tenure and seat give, which is the same. The ID decides only where a code is
sent and what the person is told.

## Payment claims (#12)

Kinds: [`../chain/kinds/claims.v1.md`](../chain/kinds/claims.v1.md).

| RPC / route | Who | Returns |
|---|---|---|
| `api_claim_payment(p_society, p)` | A resident with an open tenure on `p.flat_id` | `{ seq }`. `p = { flat_id, amount_minor, currency, paid_on, method, reference }` |
| `GET /rest/v1/payment_claims?society_id=eq.X` | A committee member sees every claim; a resident sees their own flats' | `{ seq, society_id, flat_id, flat, amount_minor, currency, paid_on, method, reference, state, proposal_seq, reason, claimed_at, age_days }` |
| `api_reject_claim(p_society, p_claim_seq, p_reason)` | Holder of `review_payment_claims` | `{ seq }` |
| `/propose` with `proposal.claim_seq` | Holder of `review_payment_claims` | As `/propose`. Only on a `receipt` |
| `api_claims_unreviewed(p_society)` | Any member | `{ count }`: open claims older than 7 days |

`state` is `open` (nobody has acted, or the receipt proposal was declined,
withdrawn or closed), `proposed` (a receipt proposal is open),
`receipted` or `rejected`.

**Refusals** (`P0001`): amount not a positive integer; currency not the
society's; `paid_on` in the future or not a date; method other than `upi` or
`bank_transfer`; reference not 6–30 letters and digits; the caller holds no
open tenure on the flat; the same reference already on an open, proposed or
receipted claim in this society; rejecting with an empty reason; rejecting or
proposing against a claim that is not `open`; a receipt proposal whose flat,
amount or currency differs from the claim's.

**What ties them together.** A receipt proposed with `claim_seq` moves the
claim to `proposed`. When that receipt posts, `claim_closed` (`receipted`) is
appended in the same transaction. If it is declined or withdrawn, the claim is
`open` again. Proposing and approving stay separate: the reviewer's own
approval counts only as their seat allows, so a receipt still needs the
treasurer **and** the secretary, or the committee above the limit.

## Notices and votes (#13)

Kinds: [`../chain/kinds/notices.v1.md`](../chain/kinds/notices.v1.md).

### Drafts and review (not chained; append-only; committee only)

| RPC / route | Who | Returns |
|---|---|---|
| `api_notice_draft(p_society, p_draft_id, p)` | President | `{ draft_id, revision }`. `p_draft_id` null starts a draft. `p = { title, body, pinned, corrects_seq?, vote? }`, `vote = { question, options[], max_picks, mode, closes_at }`. Every save is a new revision |
| `api_notice_review(p_society, p_draft_id, p_revision, p_decision, p_comment)` | A committee member other than the president | `{ ok }`. `p_decision` `approve` or `changes_requested`; a comment is required for `changes_requested` |
| `GET /rest/v1/notice_drafts?society_id=eq.X` | Committee | `{ draft_id, revision, title, body, pinned, corrects_seq, vote, required, approvals, open_change_requests, reviews: [{ reviewer, revision, decision, comment, at }], published_seq }` |
| `/publish-notice` (edge) | President | `{ notice_seq, vote_seq? }` |

- **Submitting a revision counts as the president's approval of it**, as a
  proposer's approval counts on a proposal. Other members' approvals count
  only for the revision they name: **a new revision clears them**.
- **`required`** is `ceil(2M/3)` (or the society's higher threshold), fixed
  when the draft is first saved and raised, never lowered, if the committee
  grows before publishing.
- **A change request stays open** until the member who raised it approves a
  later revision.
- `/publish-notice` refuses while `approvals < required` on the current
  revision or any change request is open. It appends `notice` and, if the
  draft has a vote, `vote_opened` in one transaction.

### Reads

| Path | Returns |
|---|---|
| `GET /rest/v1/notices?society_id=eq.X` | Published notices, pinned first then newest: `{ seq, title, body, attachments, pinned, corrects_seq, corrected_by, published_at, vote }`, where `vote` is `{ seq, question, options, max_picks, mode, closes_at, eligible_flats, flats_voted, closed, tallies?, carried?, my_flat_voted }`. `tallies` appear only once the vote has closed. For a `named` vote, `ballots: [{ flat, options }]` |

### Voting (edge function `api`)

| Route | Body | Result |
|---|---|---|
| `/ballot` | `{ society, vote_seq, options: [int] }` | `{ seq }` |

The caller must hold an open tenure on a flat that was eligible when the vote
opened, as an owner or as a tenant who lives there. Refusals: vote closed;
your flat has already voted; not eligible; more than `max_picks` options, an
unknown index or a repeated one. A committee member votes as a resident, for
their own flat, like anyone else.

A `pg_cron` job closes each vote once `closes_at` has passed, appending
`vote_closed`.

### Attachments (#59)

| Route (edge function `api`) | Who | Result |
|---|---|---|
| `PUT /notices/attachment?society=&draft_id=` | President, own unpublished draft | Raw bytes, `Content-Type` `application/pdf`, `image/png` or `image/jpeg`, at most 10 MiB, header `X-File-Name`. Returns `{ sha256, size_bytes, file_name, media_type }`; the hash is the server's, from the stored bytes |
| `GET /notices/attachment?society=&sha256=` | A member, for a published notice's file; a committee member, also for a draft's | `{ url, file_name, media_type }`: a signed link valid for 5 minutes |

`api_notice_draft`'s `p` gains `attachments: [sha256]`, in display order. Each
must have been uploaded to that draft. The list is part of the revision, so
changing it clears earlier approvals like any edit. Publishing chains the
approved revision's list as `notice.attachments`. Refusals: not a PDF, PNG or
JPEG; over 10 MiB; an attachment not uploaded to this draft; a draft already
published.

### Citing a vote

`/propose` accepts `vote_seq` and `vote_option` beside `proposal`. The server
checks that the vote is closed, single-choice, and that `vote_option` is its
`carried` option, then appends `proposal_ref` in the proposal's transaction.
Refusal: `This vote did not carry that option.` The proposal's tier, count and
approvals are exactly what they would be without the citation.

## Lookup (#14)

Any member can paste anything the product shows that identifies a record and
see what it refers to. Nothing here reveals what a member could not already
read: pseudonyms stay pseudonyms, and only the three privileged roles get the
existing *resolve* button (item 11).

### Finding

`api_lookup(p_society, p_q)` → `[{ seq, kind, matched_on }]`, ordered by `seq`.

| `p_q` | Matches | `matched_on` |
|---|---|---|
| 64 hex characters | The entry with that `entry_hash`; the entry whose `prev_hash` it is (the next one); an approval whose `proposal_hash` it is; a `document_attached` or `notice` carrying it as a file's SHA-256 | `entry_hash`, `prev_hash`, `proposal_hash`, `file_sha256` |
| 8 to 63 hex characters | The same, as a prefix of `entry_hash` only | `entry_hash` |
| A number | The entry at that sequence | `seq` |
| `N-12`, `V-41`, `C-7` | The notice, vote (`vote_opened`) or payment claim at that sequence, if it is that kind | `id` |

**A `prev_hash` match is the entry *after* the one that owns the
fingerprint**: its successor names it as `prev_hash`. Label it that way ("the
next entry links to this fingerprint"), never as the fingerprint's owner; the
owner is the `entry_hash` match, if one was found.

Case and surrounding spaces are ignored. Fewer than 8 hex characters, or
anything else, is refused: `Paste a full fingerprint, at least its first 8
characters, an entry number, or an id like V-41.` A published chain head is an
entry's `entry_hash`, so it is found the same way.

**No match is `[]`**, and the client says *"No entry in the chain this server
sent you has this fingerprint."* It never says the fingerprint is invalid or
fake: absence from a served chain proves nothing on its own (AGENTS.md item 9).

### Explaining

`api_entry_context(p_society, p_seq)` →

```jsonc
{
  "entry": { "seq", "kind", "format_version", "recorded_at", "actor", "prev_hash", "entry_hash", "body" },
  "previous": 40, "next": 42,             // null at either end
  "links": [{ "seq": 44, "kind": "approval", "relation": "approved_by" }],
  "appears_in": [{ "screen": "ledger" }, { "screen": "flat", "flat_id": "flt_…", "flat": "A-101" }]
}
```

`links[].relation`, by what the entry is:

| Entry | Relations |
|---|---|
| `proposal` | `approved_by`, `declined_by` (approvals), `posted_as` (postings), `closed_by`, `cites_vote` (via `proposal_ref`), `settles_claim` |
| `posting` | `posts` (its proposal), `reverses` / `reversed_by`, `flagged_by` (flags naming it) |
| `approval` | `approves` (its proposal), `signed_with` (`key_registered`) |
| `payment_claim` | `closed_by`, `receipted_by` (the proposal) |
| `notice` | `opens_vote`, `corrects` / `corrected_by` |
| `vote_opened` | `announced_in` (its notice), `closed_by`, `cited_by` (proposals); ballots are counted, not listed: `ballots` |
| `ballot`, `vote_closed` | `in_vote` |
| `flag` | `about` (the entries it names), `noted_by` (flag notes) |
| `proposal_ref` | `cites`, `for_proposal` |

`appears_in[].screen` names what the entry appears on, not a URL: one of
`ledger`, `flat`, `approvals`, `disputes`, `notices`, `claims`, `committee`,
`year_close`. The client maps each to its own route; these keys stay the same
when a route is renamed. The client writes the one-sentence
meaning itself from `entry` and recomputes `entry_hash` with its own verifier;
the server's `entry_hash` is shown beside it, never trusted.

## Dues reminders (#56)

| RPC | Who | Returns |
|---|---|---|
| `api_send_dues_reminders(p_society)` | Holder of `send_dues_reminders` | `{ flats, mails, skipped_recent }` |

For each flat whose `flat_dues.outstanding_minor` is greater than zero, one
mail goes to every person holding an open tenure on it: any owner, and a
tenant who lives there. The mail goes to their personal email and names only
that flat: the amount owed, what was charged and paid, and that they can tell
the treasurer they've paid from *My flat*. It names no other flat or resident.

- A flat reminded in the last 7 days is skipped and counted in `skipped_recent`.
- Amounts are written from minor units using the currency's own exponent, never a fixed `/100`.
- Mail is queued and sent like enrolment mail (*Sign-in*, *Enrolment*).

Refusals (`P0001`): the caller doesn't hold `send_dues_reminders`; **any
flat's `outstanding_minor` is null**, which refuses the whole run and sends
nothing: `A flat's dues could not be read, so no reminders were sent.` The
cell is never null (*Reads*), so a null is a server fault. Skipping that flat
would report a clean run while a flat that owes was never contacted.

Whether reminders also go out on a schedule is not settled here.
