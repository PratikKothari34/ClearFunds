# Published chain head (anchor) — v1

Once a month, the server publishes each society's chain head somewhere the
committee does not control, and the client fetches it from there itself
(AGENTS.md items 2 and 9). The hash chain shows that no entry was edited. The
anchor is what shows that none was left out, and only against a head the client
did not get from our API. Together they make the record tamper-evident: a change
cannot be made quietly. Neither makes it tamper-proof. Whoever runs the server
can still forge a whole chain, as "What the client checks" states.

Accepted on #1. Hashing is `chain/entry-preimage.v1.md`.

## Where

```
https://raw.githubusercontent.com/{anchor_account}/{anchor_repo}/main/societies/{society_id}/periods/{YYYY-MM}.json
https://raw.githubusercontent.com/{anchor_account}/{anchor_repo}/main/societies/{society_id}/latest.json
```

- **`anchor_account` and `anchor_repo` are fixed in the client at build time.**
  Never read them from our API or any runtime config. A server that could
  name the host could point the client at one it controls, and every check
  would pass against a head it minted. Changing either is a release.
- `{society_id}` is the society's id as the API already uses it (`soc_…`).
- `periods/{YYYY-MM}.json` is written once and never rewritten.
- `latest.json` is a byte-identical copy of the newest period file. It exists
  so the client can find the newest head without listing a directory: listing
  goes through `api.github.com`, which allows 60 requests an hour per IP, while
  `raw.githubusercontent.com` serves files with `Access-Control-Allow-Origin: *`.
  Do not replace it with a listing.
- The client fetches these URLs directly, never through our API.

## The file

UTF-8 JSON, keys in this order, followed by one newline:

```json
{
  "schema_version": 1,
  "society_id": "soc_gulmohar",
  "period": "2026-10",
  "head_seq": 412,
  "entry_count": 412,
  "head_hash": "9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08",
  "hash_alg": "sha256",
  "format_version": 1,
  "as_of": 1793471999000,
  "published_at": "2026-11-01T01:00:00.000Z",
  "server_signature": { "alg": "ed25519", "public_key": "…64 hex…", "signature": "…128 hex…" }
}
```

| Field | Meaning |
|---|---|
| `schema_version` | This file's layout. A client refuses any value it does not know |
| `society_id` | Must equal the society the client is checking |
| `period` | The calendar month covered, `YYYY-MM`, in the society's time zone (Asia/Kolkata today) |
| `head_seq` | The last entry recorded before the month ended. The anchor covers entries `1..head_seq` since the chain began, not just that month's |
| `entry_count` | The number of entries `1..head_seq`. Sequences are contiguous by construction, so this always equals `head_seq` (see below) |
| `head_hash` | `entry_hash` of entry `head_seq`, lowercase hex |
| `hash_alg` | `sha256`. A client refuses any value it does not know |
| `format_version` | `format_version` of entry `head_seq` |
| `as_of` | `recorded_at` of entry `head_seq`, Unix milliseconds |
| `published_at` | When the server wrote the file. **Informational only:** shown to people, never used in a check |
| `server_signature` | Optional. Ed25519 by the society's head key (the key `GET /head` signs with) over the UTF-8 bytes of the file **without this field**: the same keys in the same order, as `JSON.stringify` writes them, with no whitespace and no trailing newline. It lets nobody later deny a published head. It adds no trust, since the server is the party being checked, and v1 clients ignore it |

`head_seq`, `entry_count`, `head_hash`, `as_of` and `format_version` are the
head tuple of AGENTS.md item 9, the same values `api_head` returns.

**Sequences have no gaps.** `cf.append` gives each entry the society's
highest sequence plus one, under a lock on the society, in the same
transaction as the insert. A failed write takes its number with it, and
nothing deletes or renumbers an entry. A legitimate gap cannot occur, so a
client treats any gap as tampering, and `entry_count` always equals
`head_seq`.

**A month with no new entries is still published**, with the previous head.
Otherwise a quiet month would read as an overdue publisher.

## What the client checks

1. Fetch `latest.json`, or a named period, from the fixed host.
2. Recompute the chain from the entries our API serves, never from a hash our
   API reports.
3. **Pass** only if the recomputed hash of entry `head_seq` equals `head_hash`,
   **and** the entries received for `1..head_seq` number exactly `entry_count`.
4. Show entries after `head_seq` as *not yet anchored*: newer than the last
   publication, not unverified. An older head is a valid prefix of the current
   chain, so a `latest.json` served stale from a 5-minute cache never produces
   a false mismatch.

**What this does not catch on its own:** an operator who rebuilds the whole
chain without some entries, renumbered `1..N`, and publishes a head for that
chain. Every check above passes. Only comparing against a head the client
kept from an earlier session catches it (item 9).

## Cadence

Monthly. The publisher runs daily, writes each month as soon as it has ended,
and **by the 5th of the following month** at the latest. Months the publisher
missed are written in order on its next run. Each month is only ever written once.

If it is after the 5th and `latest.json`'s `period` is older than last month,
the client warns: *"The independent fingerprint is overdue (last published for
{period})."* The check still runs against the older file. Overdue is a warning
about the publisher, never a mismatch.

## Failures

No row of this table may ever show as passed.

| Case | Client receives | Client shows |
|---|---|---|
| Host unreachable | A network error, a timeout or a 5xx | *"Couldn't reach the independent record. The ledger has **not** been verified."* Retry is manual |
| Not published yet | `404` on `latest.json`, and the society is less than one month plus 5 days old | *"No fingerprint has been published for this society yet."* Neutral |
| Should exist but doesn't | `404` on `latest.json`, and the society is older than that | Shown like overdue, as a warning. Our API can only make this look less alarming, never make it pass |
| Mismatch | `200`, but `head_hash` or `entry_count` doesn't match the recomputation, or our API serves fewer than `head_seq` entries | Prominent: *"This ledger does not match its independently published fingerprint."* Shows the URL, both hashes and both counts. Never dismissed or retried away automatically |
| Unreadable | `200` with invalid JSON, an unknown `schema_version` or `hash_alg`, a `society_id` that doesn't match, or `entry_count` not equal to `head_seq` (a publisher bug: never guess which of the two to trust) | Not verified. Never passed |

## The account

- A GitHub account or org used only for anchors, held by someone who does not
  run the production server.
- Branch protection on `main` blocks force-pushes and deletion.
- The server holds a token that can write contents to that one repo only.
  The publisher creates period files and refuses to replace one. It reports an
  existing period file with different bytes and leaves it in place.
- **A second witness:** after writing a period file, the publisher asks the
  Wayback Machine (`web.archive.org/save/…`) to capture it. A later rewrite on
  GitHub can then be compared against a copy that neither we nor the committee
  control. This is best effort: a failed capture is recorded, and never stops
  publication.

**Publishing is off until it is configured.** Until the repo and token are set,
the publisher writes nothing. Whether a public repo may show each society's
monthly entry count is the repo owner's decision (#1 §7), and switching the
publisher on is that decision.
